小内存机器把 PHP-FPM 换成 ondemand

2026-09-02PHP / 调优

一台 1.6 G 内存的机器，装了 PHP-FPM 之后空闲时也常驻一堆 worker，加上数据库和面板，随时在 OOM 边缘。把进程管理方式从 dynamic 换成 ondemand 之后，空闲内存立刻宽松了。

三种模式的区别

  • static — 固定开 pm.max_children 个进程，常驻不回收。最稳、内存占用最高。
  • dynamic — 在 min/max 之间伸缩，空闲超过 pm.process_idle_timeout 才回收。默认值，适合访问有起伏但总体繁忙的站。
  • ondemand — 平时几乎为 0 个，来请求才 fork。没流量 = 不占内存。

改法

; /etc/php-fpm.d/zz-custom.conf
[www]
user = nginx
group = nginx
listen = /run/php-fpm/www.sock
listen.owner = nginx
listen.group = nginx
listen.mode = 0660

pm = ondemand
pm.max_children = 10
pm.process_idle_timeout = 10s
pm.max_requests = 500

php_admin_value[memory_limit] = 128M
php_admin_flag[expose_php] = off

zz-custom.conf 这类命名是为了保证在 www.conf 之后加载，同名的键会覆盖前面的值，不用去改发行版自带的文件。

改完先算一下上限

pm.max_children 不是越大越好，按单个进程的实际 RSS 估算：

ps -o rss=,cmd= -C php-fpm | awk '{sum+=$1} END {printf "%.1f MB / %d procs\n", sum/1024, NR}'
free -m

一个干净的 PHP 进程大约 30–40 MB，挂着 opcache 和几个扩展会更高。1.6 G 的机器上留 400 MB 给系统与数据库，剩下能开多少个就清楚了。

副作用

  • 空闲后的第一个请求要等进程 fork，慢几十到几百毫秒；低流量站完全无感。
  • 并发突增时 fork 有上限，超过 pm.max_children 的请求会排队，表现为偶发 502 / 504——要配合 pm.max_children 和 request_terminate_timeout 一起看。
  • 进程反复创建销毁，opcache 命中率下降，所以 opcache.enable 别关。

顺带确认的几项

systemctl restart php-fpm
systemctl status php-fpm --no-pager
ss -lx | grep php-fpm      # socket 在不在
php-fpm -t                 # 配置语法

如果 nginx 报 502 Bad Gateway，先确认 socket 路径和 listen.owner/group 跟 nginx 的 worker 用户一致——0660 的 socket 权限不对时，nginx 连不上也只会给你一个 502。
