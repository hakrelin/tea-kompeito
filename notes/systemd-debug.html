systemd 服务起不来的排查顺序

2026-09-18systemd / Linux

典型现象：systemctl start 没有任何报错，紧接着 systemctl status 却是 inactive (dead)，或者第二天发现服务半夜重启过一轮。按下面的顺序走，基本一轮就能定位。

1. 先看 status

systemctl status myapp.service -l --no-pager

重点看三样：Main PID 有没有值、Active: 后面括号里的内容、最后几行日志。带 code=exited, status=xxx 的直接跳到第 5 节的退出码对照。

2. 再看 unit 自己的日志

journalctl -u myapp.service -n 80 --no-pager
journalctl -u myapp.service --since "10 min ago"

如果这里是空的，通常意味着进程根本没被执行起来（unit 层面的问题），而不是程序内部报错。

3. 手动跑一遍 ExecStart

最关键的一步：把 ExecStart 那条命令原样拿出来，用 unit 里 User= 指定的身份跑：

systemctl cat myapp.service | grep -E 'ExecStart|User|WorkingDirectory|Environment'
sudo -u app /usr/bin/myapp --config /etc/myapp/config.yml

不带 sudo -u 直接用 root 跑，权限问题会被掩盖掉——而权限恰恰是最常见的原因。

4. 检查这四处

  • WorkingDirectory 路径是否存在（不存在报 200/CHDIR）
  • 程序文件是否有执行权限，shebang / 解释器路径对不对（203/EXEC）
  • User= 指定的用户是否存在（217/USER）
  • EnvironmentFile 里的变量是否真的被读到（systemctl show myapp -p Environment）

5. 退出码对照

  • 203/EXEC — 找不到可执行文件，或没有执行权限，或解释器路径错
  • 200/CHDIR — 工作目录不存在
  • 217/USER — User= 指定的账户不存在
  • 226/NAMESPACE — 沙箱相关的命名空间起不来（PrivateTmp、ProtectSystem 之类设得太狠）
  • 1/FAILURE — 程序自己退出的，回去看第 2 步的日志

6. Type 写错会假装成功

后台常驻的程序如果写成 Type=simple，主进程一 fork 就退出，systemd 认为"服务结束了"，于是立刻 inactive；反过来，前台程序写成 Type=forking 又没有 PIDFile，systemd 会一直等到超时再报失败。

[Service]
Type=simple
User=app
WorkingDirectory=/opt/myapp
EnvironmentFile=/etc/myapp/env
ExecStart=/usr/bin/myapp --config /etc/myapp/config.yml
Restart=on-failure
RestartSec=3
LimitNOFILE=65535

判断方法：程序默认前台跑就写 simple；会自己 daemonize 才用 forking，并且必须给 PIDFile。

7. 收尾两个命令

systemd-analyze verify /etc/systemd/system/myapp.service
systemctl daemon-reload

改完 unit 文件忘了 daemon-reload 的话，跑的还是旧配置——这点和 nginx 忘了 reload 是一样的坑。
